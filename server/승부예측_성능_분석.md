# 승부예측(MatchPredictionPage) 성능 분석

MatchPredictionPage에서 실제 예측(`ourWinChance`)이 뜨기까지 걸리는 지연 시간의 원인을
프론트부터 Henrik API 호출까지 끝까지 추적하고, "RECENT_MATCHES(최근 N경기)를 줄이면
빨라지는가/안전한가"를 분석한다.

## 1. 전체 구조 (프론트 → 백엔드 → ML → 외부 API)

```
front/src/pages/MatchPredictionPage/index.jsx
  └─ fetchPrediction(teamName, teamTag)          front/src/api/prediction.js
       └─ GET /api/predict/{team_name}/{team_tag}

server/routers/predict.py :: predict_match()
  ├─ predict_service.resolve_recent_roster(우리팀)   ─┐  asyncio.gather로 동시 실행
  ├─ predict_service.resolve_recent_roster(상대팀)   ─┘
  │     (services/predict_service.py, services/henrik_api.py 경유 - team_info/history/
  │      match_detail로 최근 매치의 5인 로스터 name#tag를 구함)
  │
  ├─ asyncio.to_thread(predict_blue_win, our_roster, opp_roster)
  │     server/ml/predictor.py :: predict_blue_win()
  │       ├─ build_player_feature(name, tag)  × 10명   ml/rolling.py
  │       │     ├─ get_puuid_by_riot_id()              ml/valorant_git.py → Henrik v2/account
  │       │     ├─ get_matches_v4(..., RECENT_MATCHES)  → Henrik v4/by-puuid/matches
  │       │     └─ get_match_detail_v4() × RECENT_MATCHES → Henrik v4/match
  │       │           (10명 전원에 대해 순차 for문 - 병렬 아님)
  │       ├─ build_team_feature(blue_players, red_players)   ml/team_feature.py
  │       │     (5명 평균/차이 피처 조립, feature_columns.pkl 순서로 정렬)
  │       └─ model.predict_proba(X)                          models/xgboost_valorant.pkl
  │
  └─ predict_service.save_prediction(db, ...)   predictions 테이블 저장
       └─ 응답: { ourTeam, opponentTeam, ourWinChance }
```

`resolve_recent_roster`/`resolve_recent_opponent`는 `services/henrik_api.py`(비동기,
자체 캐시+throttle 보유)를 쓰지만, `ml/rolling.py` → `ml/valorant_git.py`는 **완전히 별도의
동기 `requests` 기반 클라이언트**다 - 캐시도, 요청 한도 카운터도 서로 안 나눈다(3번 참고).

## 2. 지연의 실제 원인 - Henrik 요청 횟수

`build_player_feature()`가 선수 1명당 보내는 요청:

| 호출 | 횟수 |
|---|---|
| `get_puuid_by_riot_id` (v2/account) | 1 |
| `get_matches_v4` (v4/by-puuid/matches, size=RECENT_MATCHES) | 1 |
| `get_match_detail_v4` (v4/match) | RECENT_MATCHES(현재 5) |

`predict_blue_win`은 이걸 **10명(블루5+레드5) 각각에 대해 순차 for문(list comprehension)으로
호출**한다 - `asyncio.gather`도 `ThreadPoolExecutor`도 안 쓴다(세마포어/락은 있는데 실제로는
아무도 동시에 안 부름). 즉 총 Henrik 요청 수는:

```
총 요청 수 = 10명 × (1 puuid + 1 matches목록 + RECENT_MATCHES개 매치상세)
          = 20 + 10 × RECENT_MATCHES
```

`ml/valorant_git.py`는 자체 throttle로 분당 28건까지만 보낸다(Henrik Basic 키 실측 한도
30/분보다 살짝 낮게 잡음 - `services/henrik_api.py`의 `_throttle`과 동일한 알고리즘을
동기 버전으로 복제). 요청이 28건을 넘으면 60초 윈도우가 돌 때까지 그냥 기다린다.

| RECENT_MATCHES | 총 요청 수 | 28건/분 기준 대기 windows | 체감 소요시간(대략) |
|---:|---:|---:|---|
| 5 (현재) | 70 | 3 | **~2~3분** |
| 3 | 50 | 2 | ~1~2분 |
| 2 | 40 | 2 | ~1~1.5분 |
| 1 | 30 | 2 | ~1~1.3분 |

**중요**: 선수 10명의 puuid 조회 + 매치목록 조회만으로 이미 20건이라, `RECENT_MATCHES`를
아무리 줄여도(1까지 줄여도) 총 요청 수가 30건으로 분당 한도(28건)를 넘는다. 즉 **1개
요청-윈도우(60초) 안에는 절대 못 끝난다** - `RECENT_MATCHES`만 줄여서 얻는 개선은
"3분→1분대"이지, "3초"급으로 만들 수 있는 손잡이가 아니다. 근본적으로 더 빠르게 하려면
요청 수 자체의 구조를 바꿔야 한다(4번 참고).

## 3. 추가로 발견한 구조적 문제 - 레이트리밋 카운터가 두 개다

`services/henrik_api.py`(검색/팀프로필 등 일반 트래픽)와 `ml/valorant_git.py`(예측 파이프라인)는
**같은 `HENRIK_API_KEY`를 쓰면서도 서로 독립적인 throttle 카운터**를 가진다. 각자는 "나는
분당 28건 이하로 보낸다"고 안심하지만, 실제 Henrik 서버 입장에서는 두 클라이언트의 요청이
**같은 버킷**(이전 세션에서 `x-ratelimit-bucket` 헤더로 확인 - 키 하나당 버킷 하나, 엔드포인트
무관하게 공유됨)을 나눠 쓴다. 그래서:

- 사용자가 팀 프로필을 보는 동시에 다른 사용자가 승부예측을 돌리면, 두 throttle의 합이
  분당 56건까지 나갈 수 있어 실제로는 30건 한도를 넘어 429를 받을 수 있다.
- `henrik_api.py` 쪽은 429를 받으면 `HenrikRateLimitError`로 명확히 구분해서 503을 내려주도록
  이미 고쳐뒀지만(이전 세션 작업), `ml/valorant_git.py`는 429를 받으면 지수 백오프로 최대
  `MAX_RETRIES_ON_429`(5)번 재시도하다가 그래도 안 되면 **마지막 429 응답을 그대로 반환**하고
  호출부는 `res.status_code`를 확인 안 하고 바로 `.json()`을 시도하게 되어 있어(`get_puuid_by_riot_id`
  등) 조용히 실패하거나 예외로 500이 될 수 있다 - 팀 검색이 "갑자기 안 되던" 것과 같은 계열의
  문제가 예측 쪽에도 잠재해 있다는 뜻.

## 4. "몇 경기로 줄여도 안전한가" - 학습 시점 기준 확인

### 4-1. 결론부터: **이 저장소만으로는 확인 불가능**

`models/xgboost_valorant.pkl`/`models/feature_columns.pkl`은 학습 코드 없이 팀원이
`git add`가 아니라 "Add files via upload"(GitHub 웹 UI 업로드)로 올린 바이너리
파일이다(`git log --all -- server/models/*.pkl` 확인, 커밋 3개 모두 파일만 추가되고
학습 스크립트/노트북은 없음). 즉 이 모델을 실제로 몇 경기 평균으로 학습했는지 이 저장소
안의 어떤 파일에도 기록돼 있지 않다.

### 4-2. 정황 증거 - `RECENT_MATCHES=5`는 처음부터 고정값이었다

`git log --all -p -- server/ml/rolling.py`로 전체 이력을 봤을 때 `RECENT_MATCHES`는
`rolling.py`가 처음 생긴 커밋부터 지금까지 **5에서 한 번도 바뀐 적이 없다** - 모델이
`baseline_model.pkl` → `xgb_model.pkl` → `xgboost_valorant.pkl`로 세 번 교체되는 동안에도
그대로였다. `feature_columns.pkl`에 저장된 컬럼명(`blue_recent_acs`, `red_recent_kd` 등)도
"몇 경기 평균인지"를 컬럼명에 명시하지 않는다 - 숫자 자체(ACS/KD/KAST/HS%/승률 평균값)만
보고는 모델이 3경기 평균을 받았는지 5경기 평균을 받았는지 구분할 수 없다(수치 분포만
다를 뿐 스키마는 동일).

이 두 사실을 합치면: `rolling.py`는 "추론 시점 feature 계산"과 "(추정컨대) 학습 시점 feature
계산"에 같은 코드를 재사용하도록 설계된 것으로 보이고, 그 상태로 모델이 세 번 바뀌는 동안도
5로 고정돼 있었다는 것은 **학습 데이터도 5경기 평균으로 만들어졌을 가능성이 높다**는
정황 증거이지, 확정 증거는 아니다.

### 4-3. 왜 숫자를 바꾸면 위험한가

`recent_acs`/`recent_kd`/`recent_kast`/`recent_headshot_pct`/`recent_winrate`는 전부
"최근 N경기 평균"이다. N이 작을수록 표본이 작아 분산(경기 편차)이 커진다 - 즉 같은 선수라도
3경기 평균과 5경기 평균은 **분포 자체가 다르다**(평균은 비슷해도 표준편차가 다름). XGBoost는
학습 시점에 본 입력 분포를 기준으로 분할 경계(threshold)를 잡기 때문에, 추론 시점에 더
노이즈가 큰(분산이 큰) 입력을 넣으면 모델이 학습 때 안 본 값 범위로 밀려나 예측이 불안정해질
수 있다 - 이게 이전 세션에서 "학습 때와 다른 조건이 되어 예측 정확도가 떨어질 수 있다"고
말한 이유다.

### 4-4. 실제 권고

| 옵션 | 안전성 | 비고 |
|---|---|---|
| **RECENT_MATCHES=5 유지** | 안전(현상 유지) | 성능 개선 없음 - 2~3분 그대로 |
| **팀원에게 학습 시 실제 사용한 N 확인 후 그 값으로 통일** | 안전 | 가장 먼저 해볼 것 - 코드 변경 없이 답이 나올 수도 있음 |
| **N을 줄이고 그 값으로 모델 재학습** | 안전 | 학습 스크립트가 없으므로 새로 만들어야 함(범위 밖 작업) |
| **N만 줄이고 재학습 안 함** | **위험 - 비권장** | 2번 표(2장)처럼 체감 속도는 빨라지지만(70→30건), 정확도 하락 가능성을 감수해야 하고 그마저도 "3초"급은 아님(여전히 최소 1개 요청-윈도우, ~60~70초는 걸림) |

**결론: 지금 상태로 "몇 경기까지 줄이면 안전하다"고 확정할 수 있는 근거가 이 코드베이스에
없다.** 안전하게 진행하려면 먼저 이 모델을 학습시킨 사람(또는 학습 스크립트)에게 실제 학습에
쓴 rolling window 크기를 확인하는 게 최우선이고, 그게 어렵다면 재학습을 전제로 해야 한다.

## 5. RECENT_MATCHES를 안 건드리고 얻을 수 있는 안전한 개선

모델 입력 분포를 안 건드리면서 요청 수/지연을 줄일 수 있는 지점.

1. **puuid 캐싱 재사용 (반영 완료)**: `ml/rolling.py::build_player_feature`가 이제
   `db`를 받으면(`routers/predict.py`의 `predict_match()`가 넘겨줌) 먼저
   `services/riot_accounts.py::find_riot_account(db, name, tag)`로 이미 캐싱된 puuid가
   있는지 확인하고, 있으면 Henrik(`get_puuid_by_riot_id`, v2/account) 호출을 건너뛴다.
   캐시에 없거나 `db=None`(저수준 테스트 엔드포인트 `POST /api/predict`, `ml/test_predict.py`
   등)이면 기존처럼 Henrik에 직접 물어본다 - 동작 자체는 그대로 유지, 캐시 적중 시에만
   선수 1명당 요청 1건(최대 10건)을 아낀다.
2. **레이트리밋 카운터 통합 (반영 완료)**: `services/rate_limiter.py`를 새로 만들어
   `services/henrik_api.py`(이벤트 루프, `throttle_async`)와 `ml/valorant_git.py`(워커
   스레드, `throttle_sync`)가 요청 타임스탬프 상태 하나를 `threading.Lock`으로 같이
   공유하도록 통합했다 - 이제 두 클라이언트가 동시에 트래픽을 보내도 합쳐서 분당 28건
   상한을 지킨다(예전엔 각자 28건씩이라 합쳐서 최대 56건까지 나갈 수 있었음).
3. **429 처리 일원화 (반영 완료)**: `ml/valorant_git.py::api_get`이 재시도(`MAX_RETRIES_ON_429`)를
   다 쓰고도 여전히 429면, 예전처럼 그 응답을 그대로 반환하지 않고 `services/henrik_api.py`와
   같은 `HenrikRateLimitError`를 던지도록 바꿨다. `get_puuid_by_riot_id`/`get_matches_v4`/
   `get_match_detail_v4`는 `api_get`의 반환값만 확인하던 구조라 별도 수정 없이 이 예외가
   그대로 위로 전파된다. `routers/predict.py`의 두 엔드포인트(저수준 테스트용 `POST /api/predict`,
   실제 사용되는 `GET /api/predict/{team}/{tag}`)도 이 예외만 따로 다시 던지도록 고쳐서(그
   외 예외는 기존처럼 500) `main.py`의 전역 핸들러가 503 + 안내 메시지로 응답하게 했다 -
   레이트리밋을 "선수가 존재하지 않음"과 더 이상 혼동하지 않는다.
4. **10명 병렬화 (반영 완료)**: `ml/predictor.py::predict_blue_win`을 두 단계로 나눴다 -
   (1) `ml/rolling.py`에 새로 뺀 `resolve_puuid(name, tag, db)`로 10명의 puuid를 먼저
   **순차로** 다 구하고(SQLAlchemy `Session`은 스레드-세이프하지 않아서 db를 쓰는 이
   단계는 병렬화 대상에서 제외), (2) puuid가 다 정해진 뒤에는 `db` 없이
   `ThreadPoolExecutor`로 10명의 `build_player_feature`(매치목록+매치상세 조회, 순수
   네트워크 작업)를 동시에 돌린다. 세마포어(`MAX_CONCURRENT_REQUEST=6`)와 통합된
   `throttle_sync`가 여전히 분당 28건 상한을 걸므로 총 소요시간의 하한 자체는 못 줄이지만
   (2번 표에서 보듯 진짜 병목은 요청 "개수"), 선수마다 순차로 그대로 쌓이던 네트워크 왕복
   지연은 없앤다. 스크래치 테스트로 (a) puuid 사전 해석이 병렬 구간 진입 전에 끝나는지,
   (b) 10명이 실제로 여러 스레드에서 동시에 처리되는지, (c) 한 명에서 발생한
   `HenrikRateLimitError`가 정상적으로 전체 예측 실패로 전파되는지 확인했다.
